- Owner config for PWYW / pre-orders / loyalty / referrals / subscription plans lives in DB `Setting` documents with `.data/*.json` fallbacks (Phase-3 pattern, shared helper `src/lib/config-store.ts`) — editable in Admin → Commerce, sanitized against the catalog on every save.
- `.env.example`: added `CRON_SECRET` (empty; jobs also accept the Phase-3 `PRICE_ALERT_CRON_SECRET` as fallback via `src/lib/cron.ts`). No other new keys; no secrets in code.
- Shared cron guard for the three new job endpoints: unset secret → 503, wrong secret → 401 (constant-time compare).

## Honest limitations / not live-tested

- **No real Stripe account/keys exist** (owner decision: keys come after launch). Subscription checkout/portal session creation, the Stripe webhook subscription events, express buttons, and the receipt email attachment are therefore **not live-tested**: they are unit-tested at the parameter/reducer level, wired into the real webhook (signature verification unchanged), and the routes return honest `403 FEATURE_DISABLED` / `503 PAYMENTS_NOT_CONFIGURED` / `503 SUBSCRIPTIONS_REQUIRE_DATABASE` — all confirmed in the runtime smoke test. No fake success anywhere.
- **No live PayPal account**: the PayPal express path reuses the existing order flow. Note the **pre-existing** PayPal webhook is a documented skeleton (see `docs/LIMITATIONS.md`), so Phase-4 payment-completion hooks (gift delivery, loyalty earn, referral earned-flip) fire on the **Stripe** webhook; PayPal checkouts create the gift/attribution/loyalty records identically at checkout, but their completion hooks await the PayPal webhook production wiring that predates this phase.
- **No live Postgres in this environment**: every DB branch (FlashSale/Gift/Loyalty/Referral/Subscription tables) is implemented against Prisma and typechecks, but was exercised end-to-end only through the `.data` fallbacks + unit tests — the same caveat as Phases 1–3. The pre-order release job reads buyers from DB orders, so without a DB it honestly reports `orders: 0`.
- **Express checkout scope**: Apple Pay/Google Pay are presented by Stripe's hosted checkout (Payment Element express methods) — the store's buttons deep-link into that flow. No client-side Payment Element was integrated (that would add the `@stripe/stripe-js` dependency); buttons render only when Stripe is actually configured.
- **Flash-sale cap semantics**: a unit is counted when its checkout session is created (a reservation), idempotently per order. Abandoned checkouts therefore hold cap until the campaign ends — stated here rather than hidden.
- **Loyalty spend timing**: redemption is previewed to price the order and committed when the payment session is created (standard reservation semantics); if the customer abandons the provider page, points stay committed to that order id. Earn happens only on the paid webhook.
- **Receipt PDF** is a single page, WinAnsi/Latin-1 (non-Latin-1 glyphs are transliterated or replaced with `?` — product titles with `—` render as `-`). It is a receipt, not a tax invoice.
- **Subscriptions require a database** by design: without `DATABASE_URL` the checkout route refuses with `SUBSCRIPTIONS_REQUIRE_DATABASE` (the `.data` subscription store exists for tests/tooling only). Subscriber emails are kept hash + AES-GCM ciphertext; without `PII_ENCRYPTION_KEY`, cycle grants cannot email the subscriber and are skipped (logged).
- Gift delivery sends two recipient emails by design: the orchestrator's links email and a gift-note email carrying the buyer's message + claim code. Buyer confirmations never contain links/codes (unit-tested invariant).
- Referral click counting is intentionally **not** tracked (privacy-first); the panel reports orders + commissions only. Payouts are recorded-only — there is no payout integration, in code or in claims.

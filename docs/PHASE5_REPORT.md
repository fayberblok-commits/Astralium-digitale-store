## Dependency note

**`pdf-lib` added** (`^1.17.1`, the only new dependency): feature 17 must rewrite arbitrary publisher PDFs (object streams, xref streams, encryption dictionaries) to stamp every page — the Phase-4 hand-rolled writer only *creates* simple PDFs and cannot parse real ones; a hand parser risked corrupting paid deliverables. pdf-lib is MIT, dependency-free itself, and used in exactly one module (`src/lib/watermark.ts`).

## Honest limitations / not live-tested

- **No real Stripe/PayPal/Resend keys exist** (owner decision: keys after launch) — so the webhook paths that Phase 5 touches (hold gate → fulfilment skip, license issuance into the delivery email) are unit/integration-tested and code-reviewed against the real webhook, and the fraud *scoring* half was exercised end-to-end over HTTP in the smoke test (checkouts honestly 503'd at the provider step there, after assessment). Real paid-order fulfilment with holds/licenses is **not live-tested**.
- **Watermark S3 round-trip**: the stamped-download path was verified byte-level with a mocked fetch (signed GET machinery shared with Phase 1's live-MinIO-verified adapter) and against the local server for non-S3 paths; a fresh MinIO round-trip was not re-run because the sandbox restart wiped the Phase-1 MinIO binary/data (noted, not hidden). PDFs over `WATERMARK_MAX_MB` (default 50 MB) keep the presigned-redirect path unstamped — a deliberate size guard, logged.
- **Watermark email**: stamped when the buyer email is resolvable from a persisted DB order; in the zero-DB mode (orders are webhook/log-fulfilled, no order ledger) the line carries the order id only — an email is never invented.
- **Fraud velocity in zero-DB mode** uses the `.data/fraud-events.json` store (48h retention, pruned on write); multi-instance deployments should use the DB tables (same code path, verified live). The disposable-domain list is a small curated set in code — it is a signal, never a sole blocker (40 pts < 60 threshold alone).
- **License rate limiting is per-IP, per-process** (in-memory sliding window): a multi-instance deployment gets a per-instance budget; stated in code and here. It stops casual key-guessing; it is not a distributed limiter.
- **Email automation with real sends**: all three automations ran only against a mock sender in tests + the log-only email provider in smoke. Review-request and win-back read DB orders — without a database they honestly report `orders: 0` / `dbConfigured: false` (fulfilment in zero-DB mode keeps no order ledger; same caveat as earlier phases). Abandoned-cart recovery works in both modes. Cart capture is refused without `PII_ENCRYPTION_KEY` (a hash-only snapshot could never be emailed — stated in the API error).
- **A/B first paint**: the visitor cookie is set client-side, so a brand-new visitor's first homepage paint uses the dictionary headline and joins a variant from the next navigation; bucketing is stable thereafter. Exposures are recorded by the beacon (JS required).
- **Social proof in zero-DB mode** can only ever show the approved-review aggregate (orders/grants have no zero-DB ledger) — with no approved reviews it renders nothing, by design.
- Blog posts are single-locale rows (an "ar" post is its own row, not a translation link) — matches the spec's (title, slug, locale) model.
